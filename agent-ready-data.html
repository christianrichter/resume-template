Agent-ready data: let AI agents use your data, correctly and safely

Your team wants to ask questions of your data in plain language, through Claude, ChatGPT or an agent of your own. The first demo looks great. Then the answers turn out to be wrong in ways nobody notices at first: a column misread, a join that double-counts, a date filter that quietly uses information that wasn't available at the time. And nobody is comfortable giving an AI model access to production data.

I make your data ready for AI agents: a semantic layer that explains what the data means, tested query patterns for the tricky business logic, a secure access layer built on the Model Context Protocol (MCP), and a test set that measures how often the agent gets the answer right. Fixed scope, fixed price, and everything runs in your own infrastructure.

What makes data agent-ready

{% include pipeline-diagram.html steps=page.diagram band=page.diagram_band label="Agent-ready data" %}

1. A semantic layer

Every table, column and metric gets one clear name and one description, maintained with the data models (for example in dbt). The agent sees what a column means, not just its type, and the same definitions serve your analysts and dashboards.

2. Tested query patterns

The questions that are easy to get wrong (point-in-time logic, deduplication, the right join between two business dates) get a tested SQL pattern the agent can load when it needs it. Patterns are versioned and tested like code.

3. A secure access layer

An MCP server between the agent and your data: read-only SQL, every query validated before it runs, limits on cost and rate, authentication, and query logging. Error messages are written so the model can correct its own mistakes.

4. An accuracy test set

A set of real questions from your team with expected answers. It runs on every change, so you know how good the agent is today and notice when something breaks. Valid SQL is not the same as a correct answer.

Packages

Assessment · about 1 week

We look at your data, the questions your team wants answered, and the risks. You get:

  • A review of your data model and documentation from an agent's point of view
  • A first test set of 20–30 real questions, run against your data with a current model
  • A prioritized plan: what to fix, what to build, effort and cost

Build · 4–6 weeks

I build the four building blocks with your team, in your infrastructure. You get:

  • A semantic layer for the agreed scope, versioned with your data models
  • A library of tested query patterns for your business logic
  • A production-ready MCP server: read-only, validated, authenticated, logged, deployed with CI/CD
  • An automated accuracy test set with a baseline score
  • Documentation and a hand-over session, so your team can extend it

Ongoing · optional

New questions turn into new patterns and test cases, and the agent is re-tested whenever models or your data change. Monthly, cancel any time.

Built and running in production

Shibui Finance, my own product

A public MCP server that makes 60+ years of US stock market data queryable in plain English from Claude, listed in the official MCP Registry. It runs on exactly this approach: a semantic layer on dbt, PostgreSQL and DuckDB, a library of tested SQL patterns, read-only SQL with validation before every query, and rate limiting with an open-source module I wrote.

  • 46,000 production queries in the first six months
  • 3–5% error rate depending on the calling model, mostly corrected by the model itself

What I learned along the way: What 46,000 production queries taught us about LLM-generated SQL (HackerNoon). Rate limiting module: caddy-jsonrpc-matcher on GitHub.
